# Gateway v2 (Phase 1) — Spec

Implements phase 1 of [vision.md](vision.md): **trust and correctness**. Builds on
the as-built [gateway-spec.md](gateway-spec.md). Status: **proposed, not implemented**.

## 1. Scope

| ID | Feature | Module |
|---|---|---|
| F1 | Correct upstream error mapping (`502`/`504`) | gateway |
| F2 | Loopback-only bind option | gateway |
| F3 | Client API keys for `/api/**`, with per-client rate limits | gateway |
| F4 | Live Anthropic key switching (no backend restart) | gateway + backend |

Out of scope: persistent history, usage/cost, multiple routes, admin auth, encrypted
storage (later phases).

Recommended build order: F1 → F2 → F3 → F4 (F4 is the only change that touches the
backend and carries the most risk).

## 2. F1 — Upstream error mapping

**Problem.** When the backend is down the caller gets `500`.

**Requirements**
- F1.1 Connection refused / unresolved host → `502 Bad Gateway`.
- F1.2 Upstream response timeout → `504 Gateway Timeout`.
- F1.3 The response body is JSON `{"error":"upstream_unavailable"}` or
  `{"error":"upstream_timeout"}`; no internal hostnames or stack traces.
- F1.4 The request log records the mapped status.
- F1.5 Response timeout is configurable: `gateway.response-timeout` (default `120s`,
  because LLM calls are slow).

**Acceptance**
- Backend stopped → `curl -i :8081/api/x` returns `502` with the JSON above.
- Fake backend that sleeps longer than the timeout → `504`.
- Normal responses, including backend `4xx`/`5xx`, pass through unchanged.

## 3. F2 — Loopback-only bind

**Requirements**
- F2.1 New setting `GATEWAY_BIND_ADDRESS` → `server.address`. Default stays all
  interfaces (current behavior) so nothing breaks.
- F2.2 Setting it to `127.0.0.1` makes both `/api/**` and `/admin/**` unreachable
  from other machines.
- F2.3 The admin UI shows a warning banner when the gateway is bound to a
  non-loopback address (`GET /admin/status` gains `bindAddress`).
- F2.4 Docs call out the setting and when to use it.

**Acceptance**
- With `127.0.0.1`: connecting via the LAN IP is refused.
- Default: behavior unchanged; banner is shown.

## 4. F3 — Client API keys

**Goal.** Share `/api/**` with other callers without sharing the Anthropic key, and
attribute traffic.

### 4.1 Behavior
- F3.1 Operators create/list/revoke **client keys** in the admin UI.
- F3.2 A client key is generated by the gateway (`gw_` + 32 random URL-safe
  characters from a `SecureRandom`), **shown once** at creation, and stored only as a
  SHA-256 hash plus the last 4 characters.
- F3.3 New setting **Require client key** (default **off**, so existing usage keeps
  working). When on, `/api/**` requests without a valid `X-API-Key` get `401`
  (`{"error":"missing_or_invalid_api_key"}`); revoked keys get `401`.
- F3.4 The gateway strips `X-API-Key` before forwarding to the backend.
- F3.5 The request log records the client key **label** (never the key) in a new
  `clientLabel` field. Requests without a key log `anonymous`.
- F3.6 Per-client rate limit: each client key may have its own limit
  (requests/minute); if unset it uses the global limit; the global limit still
  applies to `anonymous` traffic by IP. Fixed one-minute window as today.
- F3.7 Key comparison uses constant-time hash comparison.

### 4.2 Admin API additions

| Method & path | Body | Response |
|---|---|---|
| `GET /admin/client-keys` | – | `[{id, label, last4, createdAt, revoked, rateLimitPerMinute}]` |
| `POST /admin/client-keys` | `{label, rateLimitPerMinute?}` | `201 {id, label, key, last4, ...}` — `key` appears **only in this response** |
| `DELETE /admin/client-keys/{id}` | – | revokes (soft delete, keeps label for the log) |
| `PUT /admin/settings` | adds `requireClientKey?: boolean` | updated settings |

Validation: label 1–60 chars; per-client limit 0–100000 (`0` = unlimited for that
client).

### 4.3 Data
- New file `client-keys.json` in the data dir (owner-only `0600`, atomic writes as
  today): `[{id, label, hash, last4, createdAt, revoked, rateLimitPerMinute}]`.
- `settings.json` gains `requireClientKey` (default `false`; missing = `false`, so
  old files still load).

### 4.4 Security notes
- Client keys protect `/api/**` only; they are not admin credentials.
- The admin access rules (§6 of gateway-spec) are unchanged.
- Never log or return the raw key after creation.

**Acceptance**
- With the setting off: calls without a key work as before.
- With it on: no key → `401`; valid key → proxied; revoked key → `401`.
- Raw key appears exactly once (create response) and never in `GET`, logs, or files.
- Per-client limit of 2 returns `429` on the third call for that client only.
- `X-API-Key` is absent on the request the backend receives.

## 5. F4 — Live Anthropic key switching

**Problem today.** The backend builds one `AnthropicChatModel` at startup. Both
[ClaudeController.java](src/main/java/com/example/springaiagents/ClaudeController.java)
and [SubAgentService.java](src/main/java/com/example/springaiagents/agents/SubAgentService.java)
build their `ChatClient`s once from that bean, so a key change needs a restart.

### 5.1 Chosen approach: gateway pushes the active key to the backend

1. Gateway stores keys as today.
2. On **Make active** (and at gateway start, once the backend is reachable), the
   gateway calls `PUT {backend}/internal/anthropic-key` with the active key.
3. Backend holds the key in an `AtomicReference`-backed `AnthropicKeyHolder`, and
   builds its model/clients from the **current** key, rebuilding them when it changes.
4. In-flight requests finish on the old key; new requests use the new one.

Why not a per-request header: it would put the key on every request path and in any
intermediary logs, and the backend would still need to build a client per key.

### 5.2 Requirements
- F4.1 Backend endpoint `PUT /internal/anthropic-key` with body `{"key":"..."}`; it
  returns `204` and never echoes the key.
- F4.2 The endpoint is protected: accepted only from loopback **and** with a shared
  secret header `X-Internal-Token` equal to `GATEWAY_INTERNAL_TOKEN`
  (env var on both processes; if unset the endpoint is disabled and returns `404`).
- F4.3 Backend refactor: `ClaudeController` and `SubAgentService` obtain their
  `ChatClient` from a small factory that rebuilds when the holder's version changes;
  chat memory and tools are unaffected.
- F4.4 Startup still works with `ANTHROPIC_API_KEY` (initial value of the holder), so
  existing workflows are unchanged.
- F4.5 Gateway shows per-switch result in the UI: "applied to backend" or
  "backend unreachable — will retry"; retries every 10 s until acknowledged.
- F4.6 Gateway status exposes `backendKeySynced: boolean`.
- F4.7 The backend never logs the key; the key is not written to disk by the backend.
- F4.8 Restart-based switching (`active-key.env`) keeps working as a fallback.

### 5.3 Risks and mitigations
| Risk | Mitigation |
|---|---|
| Spring AI 1.0.2's `AnthropicApi` fixes the key at construction | Rebuild `AnthropicApi` + `AnthropicChatModel` on change (verify in a spike before committing to the design). |
| Key pushed over HTTP | Loopback by default; document that remote backends need TLS or should keep restart-based switching. |
| Backend restarts and forgets the pushed key | Gateway re-pushes when it observes the backend come back (status poll). |
| Wrong key pushed → all calls fail | The gateway keeps the previous key and offers **Revert**; UI shows the last result. |

**Spike (first task):** confirm that a new `AnthropicChatModel` built from a new
`AnthropicApi` can replace the old one without touching memory/tool wiring. If not,
fall back to documenting restart-based switching as final and drop F4.

**Acceptance**
- Make a different key active → the next chat call uses it, with no backend restart
  (verified with a fake Anthropic endpoint that records the received key).
- In-flight call started before the switch completes on the old key.
- Endpoint rejects a missing/wrong token and non-loopback callers.
- Backend restart → gateway re-pushes within about 15 s; `backendKeySynced` returns to `true`.
- Key never appears in logs or in any response.

## 6. Cross-cutting

### Configuration additions
| Variable | Default | Feature |
|---|---|---|
| `GATEWAY_BIND_ADDRESS` | all interfaces | F2 |
| `gateway.response-timeout` | `120s` | F1 |
| `GATEWAY_INTERNAL_TOKEN` | unset (F4 disabled) | F4 (both processes) |

### UI changes
- Banner when bound to a non-loopback address.
- **Client keys** panel (create shows the key once with a copy button; revoke).
- **Require client key** toggle and per-client limit field.
- Key switch result line and **Revert**; `backendKeySynced` badge.
- Request log gains a **Client** label column.

### Backward compatibility
Defaults preserve today's behavior: no client key required, listening on all
interfaces, restart-based key switching still available.

### Test plan
- Unit: client-key generation/hash/verify, per-client windows, settings migration
  (missing `requireClientKey`).
- Integration (gateway, fake backend): 502/504 mapping, `401` rules, header
  stripping, per-client `429`, key-push retry.
- Integration (backend): `/internal/anthropic-key` auth rules and key swap against a
  fake Anthropic endpoint.
- Manual: extend the checklist in [guide.md](guide.md) with F2–F4 steps.

[gateway-spec.md](gateway-spec.md) (move behavior from "proposed" to as-built),

and mark phase 1 delivered in [vision.md](vision.md).

## 7. Definition of done
- All acceptance criteria above pass as automated tests (manual for the LAN check).
- Both suites green: `mvn test` and `mvn -f gateway/pom.xml test`.
- No secret appears in any API response, log line, or committed file.
- Docs updated as listed.
